● Profile Analyzer: system design and architecture

  This is a resume-vs-job-description scorer. You upload a resume PDF and paste
  a job description (JD). It returns a score from 0 to 100, the skills you have,
  and the skills you're missing. It's a monorepo with two parts that deploy
  together as one Vercel project.

  1. High-level picture

   Browser (React + Vite SPA)
          │  fetch("/api/...")   — same origin, JWT in Authorization header
          ▼
   ┌─────────────────────────────── Vercel (one domain)
  ───────────────────────────────┐
   │  /(.*)     → frontend service (static Vite build)
        │
   │  /api/(.*) → backend service (Express app exported as a serverless
  function)      │
   └────────────────────────────────────────────────────────────────────────────
  ───────┘
          │                                   │
          ▼                                   ▼
     MongoDB (Atlas)                    OpenAI Chat Completions
     users, analyses                    (optional; keyword fallback)

  - Locally: Vite runs on port 5173 and sends /api requests to Express on port
    5000 (vite.config.js (frontend/vite.config.js)). The root npm run dev starts
    both with concurrently.
  - On Vercel: vercel.json sends /api/* to the backend and everything else to
    the frontend. The browser and API share one origin, so there's no CORS setup
    in production.

  2. Backend: a layered Express API

  The backend uses a classic routes → middleware → controller → service → model
  layout:

  Layer: Entry
  Files: server.js (backend/server.js)
  Responsibility: Builds the app, adds a /api/health diagnostic, makes sure the
  environment and database are ready for every /api request, mounts the routers
   and handles errors. It exports app for Vercel and only calls listen() when
  running locally.
  ────────────────────────────────────────
  Layer: Config
  Files: config/index.js (backend/config/index.js), config/db.js
  (backend/config/db.js)
  Responsibility: Settings come from environment variables. Missing ones are
  listed instead of thrown, so /health can report them. Mongo connects lazily,
  keeps the connection and retries after a failure. This suits serverless cold
  starts.
  ────────────────────────────────────────
  Layer: Routes
  Files: auth.routes.js (backend/routes/auth.routes.js), analysis.routes.js
  (backend/routes/analysis.routes.js)
  Responsibility: Wire each URL to its middleware chain and controller.
  ────────────────────────────────────────
  Layer: Middleware
  Files: auth.js (backend/middleware/auth.js), upload.js
  (backend/middleware/upload.js), errorHandler.js
  (backend/middleware/errorHandler.js)
  Responsibility: requireAuth and optionalAuth check JWTs. Multer keeps the
  upload in memory (PDF only, 4 MB max). Every error is turned into a {
  message, field? } response.
  ────────────────────────────────────────
  Layer: Controllers
  Files: auth.controller.js (backend/controller/auth.controller.js),
  analysis.controller.js (backend/controller/analysis.controller.js)
  Responsibility: Check the input and set HTTP status codes. Business logic
  stays
  out of them.
  ────────────────────────────────────────
  Layer: Services
  Files: auth, analysis, pdf, compare, openai, skills
  Responsibility: All the domain logic (see below).
  ────────────────────────────────────────
  Layer: Models
  Files: User.js (backend/models/User.js), Analysis.js
  (backend/models/Analysis.js)
  Responsibility: Mongoose schemas. Each has a toPublic() method that controls
  what the client sees, so it never gets the password hash or the resume text.
  ────────────────────────────────────────
  Layer: Utils
  Files: utils.js (backend/utils.js)
  Responsibility: HttpError(status, message, field) and validation helpers.

  The main flow: POST /api/analyses

  optionalAuth → uploadResume (multer, memory) → controller.create
     → analysis.service.createAnalysis
          1. pdf.service.extractPdfText(buffer)   — pdf-parse; rejects scanned
  or empty PDFs
          2. compare.service.compare(text, jd)    — strategy with a fallback:
               ├─ OpenAI (if OPENAI_API_KEY): strict JSON schema, temperature 0,
               │  45 s timeout, prompt-injection guard, output cleaned up
               │  (dedupe, keep each skill in one list, clamp the score)
               └─ on no key or any failure → keyword-v1: whole-word regex
  matching
                  against the skills.js dictionary; score = present / wanted ×
  100
          3. Analysis.create({...result, engine})  — user is attached only if
  signed in
     → 201 { analysis }

  Key design decisions:
  - Graceful degradation. An OpenAI outage, a used-up quota or a bad key never
    blocks the user. It's logged, and the keyword engine scores the resume
    instead.
  - Engine provenance. Each analysis records engine (openai:gpt-4o or
    keyword-v1). The extracted resume text and the JD are stored too, so past
    analyses can be re-scored without another upload.
  - The PDF itself is never stored. Only the extracted text is saved.
  - Errors are field-aware. The field value lets the UI show each error next to
    the input that caused it.

  Auth

  This is stateless JWT auth. On sign-up, the password is hashed with bcrypt
  (cost 12) and the server returns { token, user }. The token is signed with
  JWT_SECRET and expires after 7 days by default. Analysis works without signing
  in, but history (GET /api/analyses, the last 20) needs a token.

  3. Frontend: React SPA

  - App.jsx (frontend/src/App.jsx) is a single landing page: Header → Hero →
    Analyzer → HowItWorks → Footer, plus an AuthDialog modal.
  - AuthContext.jsx (frontend/src/auth/AuthContext.jsx) holds the global auth
    state: the current user, which dialog is open, and the sign-in, sign-up and
    sign-out actions. On load, it restores the session by calling /auth/me with
    the saved token.
  - lib/api.js (frontend/src/lib/api.js) is a thin fetch wrapper. It adds the
    Bearer token (read from localStorage inside try/catch) and turns failed
    responses into ApiError objects that carry status and field.
  - lib/analysis.js (frontend/src/lib/analysis.js) mirrors the server's checks
    on the client (PDF type, 4 MB limit, 20k-character JD) and holds the copy
    for each score band.
  - Analyzer.jsx (frontend/src/components/Analyzer.jsx) is a small state
    machine: form → checking → results. It sends a FormData request. It also
    waits at least as long as the loading-step animation, so the steps still
    play when the server answers instantly.

  4. Cross-cutting concerns

  - Security: the OpenAI key stays on the server. Passwords are hashed with
    bcrypt. The API's JSON body limit is 100 KB. The prompt tells the model to
    treat the resume and JD as data, not instructions.
  - Vercel constraints shape the code: uploads are capped at 4 MB because of
    Vercel's 4.5 MB body limit, the database connects lazily, the pdf.js worker
    is loaded inline, and Atlas has to allow 0.0.0.0/0.
  - Operability: /api/health tells you exactly what's misconfigured (missing
    environment variables, or why MongoDB can't connect) without digging through
    logs.

  5. Things I noticed along the way

  - Stale comments: models/Analysis.js (backend/models/Analysis.js) still says
    the AI step will be "added later" and that keyword-v1 is used "now". OpenAI
    scoring has already shipped.
  - Stray log file: s.tmp.log is committed to the repo. It looks like a stray
    file that should be deleted and added to .gitignore.
  - Anonymous analyses are stored: an analysis from a visitor who isn't signed
    in is still saved, including the full resume text, but no user can ever see
    it again. Consider not saving these, or deleting them after a set time (for
    example with a MongoDB TTL index), for privacy.
  - Outdated description in DECISION.md: DECISION.md is really the original
    prompt history, and it still describes Cohere. The code now uses OpenAI.

● No, the app doesn't use RAG. I searched the code for embeddings, vector
  stores, retrieval, and libraries like LangChain, Pinecone, Chroma or FAISS,
  and found none of them.

  What it does instead is a single prompt call. openai.service.js
  (backend/service/openai.service.js) sends one Chat Completions request:

  - System message: fixed instructions for picking out the job's skills, sorting
    them into present and missing, and giving a score.
  - User message: the whole resume text (cut off at 30,000 characters) and the
    whole JD, wrapped in <resume> and <job_description> tags.
  - Reply: must follow a strict JSON schema, { score, present, missing }.

  Nothing is retrieved. Both documents go straight into the prompt, and the
  model compares them in one pass. The keyword fallback in compare.service.js
  (backend/service/compare.service.js) is plain regex matching against a fixed
  list of skills in skills.js, not retrieval either.

  Why that's fine here: RAG is for when the knowledge you need is too large to
  fit in a prompt, or keeps changing, so you look up only the relevant pieces.
  Here the input is just two short documents (a resume and a JD), which easily
  fit in the model's context. Retrieval would add cost and complexity, and it
  could cause misses by dropping parts of the resume.

  Where RAG could make sense later:
  - Searching past analyses: for example, "find resumes in my history that match
    this new JD." You'd store embeddings of the saved resumeText and search
    them with MongoDB Atlas Vector Search.
  - A large, changing skills taxonomy: for example, mapping skills to a big
    standard catalog like O*NET or ESCO, instead of the hard-coded skills.js
    list.
  - Grounded improvement tips: pulling relevant guidance from a knowledge base
    to suggest how to close the gaps in the missing skills.

  the order of the doc's six phases, mapped to the files that exist today.
  First, four things in the doc to fix or adjust before you start.

  Before you start: issues in the doc

  1. Typo in the Summary: the Repo line reads backe (Eanxpress + Mongoose). It
     should be backend/ (Express + Mongoose).
  2. The keyword engine can throw. keywordCompare() in compare.service.js
     (backend/service/compare.service.js) throws a 422 HttpError when a job
     description contains no skills from skills.js. Many third-party postings
     will hit that. The agent must catch the error per job and skip that job, or
     one bad posting can fail the whole run.
  3. Where run state lives. The doc says App.jsx holds runId, but Results is
     rendered inside Analyzer.jsx (frontend/src/components/Analyzer.jsx). It's
     simpler to keep the run in Analyzer, which already owns result, and leave
     App.jsx alone.
  4. Tests: there's no test runner yet. Node 22's built-in node:test fits the
     project's minimal-dependency style, so no Jest or Vitest is needed.

  Choices that differ from the doc

  - Run expiry: anonymous runs get an expiresAt date with a TTL index. The doc's
    version, a TTL that applies "when there is no user", can't be built:
    MongoDB can't limit a TTL index to documents where a field is missing.

    carries on. The main case is a posting with no skills the keyword engine
    knows while OpenAI is unavailable.
  - Retries: a run saves the list of jobs it chose to score, so a retry doesn't
    search again.

  How it works

  - Search on upload: after an analysis is saved, a job search starts in the
    background (waitUntil). If it can't start (daily limit reached, or no job
    source configured), the analysis still succeeds and the response carries
    jobRun: null with a jobRunError message.
  - One worker per run: a worker claims a run for 2 minutes and extends that
    claim every time it saves progress. If the worker dies, the claim expires
    and the cron sweep hands the run to a new worker. A run gets at most 3
    attempts.
  - Cancelling: once a run is cancelled, the worker's next save fails, so it
    stops within about one job. A cancelled run is never overwritten as "done".
  - Access: a signed-in user's run is theirs alone. An anonymous user sends
    X-Run-Token; only a hash of the token is stored. A run that doesn't exist
    and a run that belongs to someone else both return the same 404.
  - Polling: ?since= takes the last match id the client has seen and returns
    only newer matches.
  - Daily limit: 10 searches per user, or per IP when signed out (stored as a
    hash, not the raw IP). The IP comes from x-real-ip only on Vercel, because
    anywhere else a client could fake that header.

  Differences from the doc

  - File names follow the repo's existing pattern (jobRun.controller.js), not
    the doc's controller/jobRuns.js.
  - Token only for anonymous runs: jobRun.token is returned only when the user
    is signed out. Signed-in users use their normal session.
  - Your chosen location is kept: if you set a location yourself, the search
    never widens past it. Otherwise it widens as the doc describes.

  Before you deploy

  1. Set the variables in your Vercel project: ADZUNA_APP_ID, ADZUNA_APP_KEY,
     ADZUNA_COUNTRY and CRON_SECRET.
  2. Cron schedule: it's set to once a day (0 6 * * *), the most often the Hobby
     plan allows. That means a stalled run could wait up to a day to be
     resumed. On Pro, change it to */5 * * * *. Vercel crons run only on
     production deployments.
  3. Time limit: background work counts against your plan's function time limit.
     A full run (profile, search, about 25 scoring calls, 4 at a time) could
     approach it. Time one on a preview; if it runs out, the cron sweep resumes
     the run later.
  4. Not done in this phase: rate limiting on POST /api/analyses and the auth
     endpoints is still open from the doc's known-gaps list. The README API
     table gets updated in Phase 5.
